# Sign-in Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add invite-only Clerk username/password sign-in, verified-email password recovery, and a separate seven-member sample-data demo entry to Fish Upon The Sky.

**Architecture:** Keep the existing React + Vite application and add a Clerk-backed session gate at the app root. Signed-in users resolve to one provider-assigned member ID; demo users explicitly choose a sample member and use the current in-memory prototype. Real group data remains local/sample until a separate persistence design is approved.

**Tech Stack:** React, Vite, existing CSS tokens, Framer Motion, Clerk's currently supported React SDK.

**Spec:** `docs/superpowers/specs/2026-11-22-sign-in-design.md`

## Global Constraints

- Real access is invite-only for the existing seven people: Bảo (`bao`), Hằng (`hang`), Diễm (`diem`), Quỳnh (`quynh`), Quốc Anh (`quoc-anh`), Thư (`thu`), and Thiên (`thien`).
- The owner sends only seven invitations and assigns each canonical member ID to one account exactly once; the app denies missing or unknown mappings.
- Real sign-in uses a custom username and password; password recovery uses the account's verified email.
- Demo selection must never create a real provider session or access production records.
- Use the existing citrus `#FFA62B`, sky `#86C5FF`, Amalfi `#2E5AA7`, cream `#F8E6A0`, white `#FFFFFF`, and text `#202A35` tokens.
- Keep CharSen2/Poffly Rounded font roles, 1.25 type scale, 8px spacing rhythm, responsive behavior, and reduced-motion support.
- Keep provider secret keys and credentials out of client code, committed files, and local storage. Only the public publishable key may be exposed to Vite.
- Use `Logo/Logo.svg` for the sign-in and planner brand marks; the two attached palette/font images are references, not page artwork.
- Do not add shared group-data persistence in this feature.
- Do not add or run automated tests unless the user asks; use the existing build and focused manual UI checks.

## Review Focus

- Missing Clerk key: the app stays on the sign-in screen, clearly explains that real sign-in is not configured, and still offers demo; it never treats a demo selection as authenticated.
- Unverified or unknown recovery email: recovery does not reveal whether an account exists and only provider-verified email can complete reset.
- Signed-in account with no or invalid trusted `memberId`: deny access to member-specific actions and show an account-setup message; never fall back to Bảo.
- Real session identity: member-specific voting uses the signed-in member ID and offers no identity switcher; demo retains its own member picker.
- Narrow viewport, keyboard navigation, and reduced motion: the form remains usable and state changes remain understandable.

### Task 3: Gate the planner and bind real identity

**Files:**
- Create: `src/auth/ClerkAuthRoot.jsx`
- Modify: `src/App.jsx`
- Modify: `src/auth/AuthEntry.jsx` (only if provider state requires presentation changes)
- Modify: `src/styles.css`

**Interfaces:**
- `ClerkAuthRoot({ publishableKey, members, onEnterDemo, renderPlanner })` mounts Clerk only when configuration exists and exposes signed-out, loading, mapped-user, and unmapped-user states. `members` comes from the planner's canonical member list; `renderPlanner` avoids an import cycle while passing the resolved identity to `PlannerApp`.
- `PlannerApp({ currentMemberId, identityMode, onExitDemo, onSignOut })` owns the existing planner/sample state.
- `identityMode` is either `'demo'` or `'authenticated'`; only demo mode may change `currentMemberId`.
- `currentMemberId` in authenticated mode comes only from provider-controlled `user.publicMetadata.memberId` and must match one of the seven IDs.
